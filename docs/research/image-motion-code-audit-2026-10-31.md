# 整幅图片弹奏：现有播放器连续性审计

2026-10-31。范围：本地实际源码、打包脚本、manifest 与确定性状态采样；未做新素材、未修改 public、未以代码推断代替本轮浏览器像素/流畅度评审。保持每一生产帧含完整猫、双臂双爪和乐器，不采用身体底板加独立手臂。

## 实际播放路径

`public/full-frame-character.js:1–6` 当前使用 `guitar-pluck-v1`，不是历史 `guitar-motion-v1` 的 27 边转场图。后者仍在构建清单中，不能据它存在就声称跨键转场可用。

- 钢琴与架子鼓：`full-frame-character.js:30–35,141–145` 按最新确认输入选完整姿态，画布直接替换；当前没有它们的连续运动插值。这是明确的离散pose切换。
- 吉他：`guitar-motion.js:24,29–34` 每次输入立即换目标code、清空paintedAt，第一幅强制目标接触态；之后64ms回到抬爪态。它是“接触→恢复”，不是连续的“准备→下落→接触→回弹”。接触不延迟的初衷有助音画响应，但从之前任意姿态直接跳到新接触态会产生不连续。
- 跨琴位：`scripts/prepare-guitar-pluck.py:15–31` 为每个琴位单独生成 up/down 与七张RIFE中间图；manifest明确说大幅换位直接选新整幅画。A→K 等跨code连接未生成。快按取消旧恢复是有意行为，测试 `scripts/guitar-motion.test.mjs:20–21` 正在保证这个事实；它保证不排队补演，不保证像素/位置/速度连续。

## 可证实的跳变来源

1. **64ms太短，七张中间图并不等于看得见七张。** 实际函数按60Hz理想采样，输出 contact → cell5 → cell3 → cell1 → up（约66.7ms）。见 `artifacts/image-motion-code-audit-2026-10-31/state-trace.json`。60Hz采样无法展示全部9个状态；再提高离线插帧数不会解决同一时长的显示采样上限。这里不是测得设备丢帧，而是现有时长与采样的必然选择。
2. **新输入直接从旧任意状态切到新完整接触图。** `strike` 不保留当前phase、手的位置/速度，也无source→target过渡边。再流畅的单琴位恢复也覆盖不了这个接缝。
3. **运动和停驻图的分辨率/压缩不同。** atlas每格640px（WebP quality86）放大到1254；ready则直接画1254px JPEG抬爪图。见打包脚本17–29及renderer115、125、143。可能产生清晰度跳变；是否肉眼可见须同机位实图/播放确认，不能仅凭格式认定。
4. **预取了编码文件，不代表全部图已解码。** renderer84–87先取51份blob，仅解码KeyA up/atlas；bitmap缓存117行最多4份。跨多个琴位可能重复解码；139行等待asset时冻结visualClock，避免花掉没看到的动作，但停顿仍可能可感知。未测实际decode毫秒数，不将其称为已证明主因。
5. **独立生成的端点可能本身不一致。** 打包脚本没有配准、接触轨迹或身体背景一致性检查；这是素材风险，需要实图对比，当前审计不声称已测出漂移像素。

## 先验证最便宜的一段，不扩素材规模

建议隔离对比页仅试现有猫的A/S/K三个琴位：同音连击、近位交替、远位切换各一段。首个分支只调整准备/接触/回弹节奏和统一640显示素材，保留原版可切换。禁止先对17键各做更多图。

具体验收：60/120/180 BPM；同键4Hz与6Hz；A-S、A-K交替；击发发生在恢复中途；长按、停止及冷/热缓存。声音立即发出、不排队补演；一次输入至多一个接触，停下不能补动作；观察手掌是否隐现/重影、目标是否正确、跨键是否整体跳位、接触相对音频的偏移。

素材路线先试**同一固定机位/同一完整场景的短动作原片**，人工/模型选择准确接触和抬爪锚帧后，只在邻近、结构一致帧之间做离线插帧；不得再拿差别很大的两张独立姿态期待RIFE修正解剖。关键未知是“新输入在动作中途到来时如何连接”，必须看真实连续交互，离线顺播短片通过不等于交互通过。

如果一组端点在离线短片中手/琴接触都不成立，停止调播放参数，修素材而非继续加帧。对整个角色做长crossfade会引入重影，不能当作自然动作。若固定短片仍无法满足自由快速换键，报告可达边界，不把完整歌曲视频冒充逐键控制。
