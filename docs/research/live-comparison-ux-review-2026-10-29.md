# 上线三版弹奏对比页：独立 UI / 使用体验审查

审查日期：2026-10-29。审查者：独立 UX / 用户心理评审代理；不是该页或模型的 builder。

对象：<https://miao-beat.pages.dev/labs/character-compare/>。生产代码依据为当前 `public/labs/character-compare/index.html`、`play.css`、`play.js`、`three-renderer.js`。主代理另做有声试玩与录屏，本评审不替代那份动作/声音实测。

## 结论

作为作者核验“三路是否接收相同输入”的技术台，页面可理解，边界提示诚实，三栏和统一视角确实有比较价值。作为第一次打开就想玩的音乐小玩具，当前仍有明显距离：先读技术解释和调试控制，后看到半个角色，琴键在首屏之外；用户获得的第一印象是“帮作者验收”，不是“我和猫一起玩”。

本轮没有建立新的功能性 P0：没有测试发声、音画延迟、快弹、停止、触摸或真实移动设备。已知美术门禁仍然是 P0 的产品交付边界：不能以此页可操作或引擎接通，宣布新猫替换原版成功。技术样机页面可保留；把本页包装成已完成的角色升级不可接受。

## 证据范围

- 实际操作：独立隐藏 IAB 标签打开生产地址，1280×720；检查初始布局，切换“双手”“脸部”，滚动到琴键，再点中栏“单独看”。未打开声音，未按旋律/和弦键，未启动演示，没有动主代理的标签页。
- 实际看见：三栏最后均有角色画面；原版状态由“完整画面就绪 · 动作加载中…”变为“原版动作已就绪”；Three / Godot 出现各自就绪文字。这证明本轮静态显示和对应 UI 状态，不证明动作或全部资源完整。
- 只读检查：输入/加载流程、solo 与视角处理、CSS 响应式规则。代码推得的首击行为及移动布局风险分别标注，未冒充有声或移动实测。
- 参考：直接看了获批原图 `public/character/instrument-scenes-v1/guitar/idle.jpg` 和 `artifacts/reference-progress-comparison/progress-face.png`。后者是独立的最新静帧研究，不是本页已经替换的模型；本评审不会把二者混为一谈。

## 第一次打开能否懂、能否马上好玩

**能懂的部分（实见）：** 标题“三版弹奏对比”、开头 ASDFGHJK 指令、绿色“打开声音”、技术样机声明都清楚。“同一份声音，不会叠三遍”解除了三路音频混在一起的疑虑。原版 / Blender→3D网页 / Godot 的三列标题可供作者定位实现；三栏的“单独看”也很容易发现。

**首屏层级问题（实见）：** 1280×720 初始画面中，舞台卡片从约 y=405 开始，角色从约 y=505 开始；猫与吉他下半部在折下，所有琴键在折下。按键用户可以凭说明直接敲键，但点击用户要先找“下方琴键”。慢/快演示、停止、全身/双手/脸部、头部微动作、转动、三栏并排，在发生第一声之前均处于同一操作层级。

**限定而非夸大的判断：** 向下滚约半页后，可以把三栏舞台和八个旋律键放在同一屏，和弦行仍靠下；因此不是“永远不能同时看猫和琴键”。问题是页面没有带新用户进入这个可玩位置，首屏和一次整页滚动都不是好位置。

**首击风险（代码可证，未实听）：** `play.js:31–32` 在声音未就绪时只调用 `prepare()` 并返回 `false`；该次音符不会在加载后重放。直接点琴键/按 A 的用户会启动加载，却没有完成那一次声音和三路 strike。指令确实先要求打开声音，但轻玩具通常会被直接点角色/琴键尝试。需要主代理用冷启动直接按 A 复核实际感受，不能在本报告声称已听见丢音。

**状态文案（实见，环境限定）：** 本轮隐藏标签第一次截图显示“页面离开，演奏已停止。”，并非欢迎/就绪提示；对应 blur / visibility 停止处理是合理保护，但在从未演奏时会留下事件口吻。隐藏 IAB 可能影响触发，不能外推所有正常前台打开均如此。

## 三栏比较是否公平、动作是否可读

三列同宽、相同输入、全身/手/脸统一切换，是良好的技术比较骨架。加载状态各列可见，也没有用一个总“成功”掩盖全部引擎。

但当前**统一按钮不等于匹配裁切**。在实见脸部视角里，原版眼线和头顶明显高于两栏 3D，3D 的脸更靠下；中栏背景较灰，右栏偏亮黄，地面/阴影也不同。这足以干扰“哪个更好看”的直接判断：当前页面同时比较角色造型、相机、材质和引擎灯光，不能由此归因某引擎天生更好。

“双手”只放大至约 1.25 倍，还保留大半身体，并非紧凑的触弦接触证据视窗。能帮助定位手，不能代替逐帧手弦接触评审。实际动作可读性、快速输入是否振动或重置、接触时刻是否同步，本轮未测。

点“单独看”后，中栏成为最大宽度 850px 的方形舞台，720px 高屏里舞台明显超过可视高度，键盘进一步下移。卡内按钮仍叫“单独看”；返回“三栏并排”在上方非 sticky 视角行。它适合放大看资产，但当前不是方便连续弹奏的 solo 模式。

移动端为**代码风险，未实机验证**：`@media(max-width:850px)` 把三栏顺次堆叠，而键盘仍位于全部三栏之后；小屏点击输入更可能与正在观察的角色分离。不能用桌面截图声称移动体验通过。

## 原版更容易被喜欢的可能原因

以下是对实见视觉的专家推断，不是用户研究或偏好统计。

- 原版有矮胖梨形身体、圆方脸、自然侧目、短绒和较柔和的口鼻转折；猫像是自己有注意力的角色。两栏线上 3D 更平直的头顶和脸侧、圆眼的正向凝视、较硬的奶油色口鼻区、弱毛感，让它更像模型演示。角色好感的差距不能靠“三维”“真实引擎”的标签抵消。
- 原版猫与吉他构成一个完整而松弛的姿态；小手与乐器的尺度容易一眼读懂。3D 在静态缩略图里也能读出弹琴，但手与前臂更块状，乐器轮廓和接触较生硬；用户更可能先看到制作瑕疵，再注意反馈的新能力。
- 3D 的潜在用户收益是自然的连续动作、微表情与可转视角。当前首页优先呈现的是 Canvas、GLB、Three.js、WebGL、Godot，而不是这些可感知收益。对作者是有效信息，对普通试玩者不构成“我再弹一会”的理由。

分享动机目前更接近“你帮我看看哪个方案好”，而非“看这只猫跟着我弹了一段”。这是本评审的推断；没有点击、留存或转发数据。不建议为了分享欲立即增加社交功能。先恢复一眼喜欢的角色和一按就有回应的体验。

## 最多三项优先修复

1. **P1 — 让第一屏就是可玩的舞台。** 压缩开头；保留一行技术样机提示；默认只露出打开声音/演示与琴键，把头部、orbit、制作/引擎细节收进“比较设置”。让完整猫/吉他和旋律+和弦键在常见桌面高度同时可见；小屏用明确的原版/网页3D/Godot切换，保持共同键盘与当前舞台邻近。solo 的“返回三栏”放在同一卡片，舞台按可用高度约束。验收：1280×720 首次打开无需找滚动位置可完成点键并看整猫；390×844 实测点键时可见当前猫及手。
2. **P1 — 消除首声前的无反馈，并把准备状态说清。** 冷启动直接点/按键时，明确提示“正在准备声音，请再按一次”，或由合适的初始化流程进入能弹状态；避免静默吞下用户第一意图，也不要把加载期排成一串稍后爆发的音符。区分音色准备与三栏加载；缺一栏时标明部分就绪。首次无演奏的 blur 不应覆盖为“演奏已停止”。验收：冷启动先点琴键、先按 A、先点演示三条路径均有明确可理解的反馈；主代理实听验证声音/动作和停止。
3. **P1 — 校准比较，再问用户喜欢哪版。** 全身/手/脸按相同可见范围、眼线、接触区域校准；统一背景和基准光，保留另一个“引擎原生显示”选择供作者检查。把“同一模型的两种运行方式”解释成一句普通话；始终区分线上技术模型与最新静帧研究。验收：匹配相机的三组截图可直接比较脸/手/体型；对偏好结论同时记录原版造型差距，不把灯光差距解释为引擎优劣。
