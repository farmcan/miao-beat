# Blender 吉他猫一期：参考、复用选择与动作评审

2026-10-28。目标是公开独立测试页的完整猫+吉他连续拨弦，先证明接触与连按成立，再决定是否替换正式角色。调研和建议不等于实际渲染、用户自然度认可或移动端验收；本文件不声称这些已经完成。

## 先给选择

首版采用 Blender 离线制作和渲染 → 完整场景 WebP 图集 → 网页 canvas 选帧。复用站内吉他采样、按键与媒体导出。Blender 的模型、灯光、骨骼和材质留在制作阶段；网页每帧只画一幅完整猫、相连双爪与吉他，不用身体底图拼手臂。

Blender 本身并不会自动消除网页重触发的跳变。把同一条动作每次重播帧0，或者把用户输入排成待播视频队列，依然会出现“瞬移”和“一按多弹”。最值得借鉴的是 FretDance 对当前拨片位置和下一音间隔的处理，而不只是其模型外观。

## FretDance中可以直接学的动作逻辑

[实际代码 `animate.py`](https://github.com/highmore9501/fretDance/blob/f63d1a6e5110a10d92b5c18fcdbd100e421b1878/src/animate/animate.py)：

- `leftHand2Animation` 先从三个参考点计算琴面法线，分别产生准备、接触和松开的控制目标；换弦才主动抬指，同弦换品可以滑行。说明应先标定接触几何，不能靠“猫在弹琴”的泛泛动作替代。
- `rightHand2Animation`（512–570行）把动作拆为触弦、拨过、空档时回准备，拨弦时长约1/15秒，扫弦时间加倍；下一音太近时不插入多余的完整归位动作。
- `ElectronicRightHand2Animation`（572–635行）根据拨片当前在最低弦下还是最高弦上决定下一击方向，保留拨后位置，而不是每音都返回同一个预备点。

源文件和MIT许可已原样取回到 `artifacts/blender-reference-audit-2026-10-28/fretDance-f63d1a6/{animate.py,LICENSE,pyproject.toml}`，尚未在产品中执行或移植。可以直接移植 `rightHand2Animation` 的时序骨架：保留 `FPS/15`、扫弦倍时、下一音够远才回位的条件，把 `caculateRightHandFingers` 产生的人类手指字典替换为本站猫爪的ready/played目标点；这会少引入整套左右手组合解算和numpy依赖。若复制函数或实质改写，须随衍生文件保留MIT版权与完整许可。`calculateRightPick` 在 `src/hand/RightHand.py:482–537`，但依赖角色标定JSON；不能把它无配置直接调用于本猫。Blender导入层 `src/fret_dance_addon/make_animation.py` 还直接访问旧 `action.fcurves`，实际安装新版Blender时需先查Action/slot兼容，不能声称即装即用。

本猫尚未支持逐指演奏。主任务已直接查看作者古典吉他视频第一p，并注意到作者标出的无名指bug；该观察和本研究只读仓库来源的证据分开记录。

## Blender Kiln：可复用的制作检查，而非已验证猫动画

[elithril/blender-kiln固定提交](https://github.com/elithril/blender-kiln/tree/4b170be2756d87d0d5a1b8e7aebef5fd61c7f771)为 `4b170be2756d87d0d5a1b8e7aebef5fd61c7f771`（2026-10-12）。实际读LICENSE确认MIT，版权2026 Nicolas Dolphens；这是第三方项目，**不是Blender官方项目**，只是支持Blender Foundation的官方Lab MCP。没有全局安装或执行它，也没有把它README的自测分数当作本猫质量证据。

已读固定提交的 [`plugin/references/texturing-strategy.md`](https://github.com/elithril/blender-kiln/blob/4b170be2756d87d0d5a1b8e7aebef5fd61c7f771/plugin/references/texturing-strategy.md) 和 [`validation-checklist.md`](https://github.com/elithril/blender-kiln/blob/4b170be2756d87d0d5a1b8e7aebef5fd61c7f771/plugin/references/validation-checklist.md)。适合本次直接采用的做法：

- 卡通对象优先少量明确区分的材质：木质示例粗糙度0.7/金属度0，金属示例粗糙度0.2/金属度1；这些是起测配方，具体猫毛/清漆/眼睛仍看实际光照渲染调整。
- 检查每个长部件的两端接合，而不只看远景整体：本项目对应肩肘、腕爪、琴颈与琴体、弦端与琴桥。
- 导出后检查实际交付文件，不只看blend预览；材质纹理丢失要明确失败。我们交付整图atlas，检查对象是atlas解码帧与最终导出MP4，而非GLB validator通过即可。
- 材质节点不一定能GLB直接导出；首版离线图像保留Blender材质渲染，无需为未采用的GLB路线增加贴图烘焙步骤。

Kiln自身要求Blender4.4+，README将4.4/4.5列为API可用但未实测，不应替作者扩张兼容承诺。它含可选AI模型服务与MCP服务器要求，本轮纯脚本/离线渲染不需要启用这些链路。

## 线上方案比较

| 方案 | 首版匹配度 | 具体边界 |
| --- | --- | --- |
| 完整场景WebP图集 + canvas | 本轮首选：机位和影子一致，逐帧可控，复用现有截图/媒体导出，无额外3D运行时。 | 24张640方图若一次解码为6×4图集，RGBA像素约37.5MiB；网络压缩体积与解码内存不同。先压测，不能只报WebP文件小。图集不能补出未渲染的任意姿势；密集输入须明确合并规则。 |
| 完整视频片段 + seek/播放 | 适合看连续动作成品和模型参考，不是首版即时触发主通路。 | 播放/seek与解码有异步边界，不可假定设置currentTime马上显示目标帧；频繁重启短视频很容易复现延迟和多动作。`requestVideoFrameCallback` 可观察真正提交的帧，但不保证随意seek即时呈现。 |
| GLB + three.js实时渲染 | 后续若允许完整3D运行时，可连续解算、按当前姿态重触发与混合。 | 要适配模型/蒙皮、材质/灯光差异、GPU上下文/设备性能、导出完整画面。当前项目约束禁止网页拆体拼臂，不把实时独立肢体试验直接上生产。首版不为一个拨弦引入整个运行时。 |

[MDN视频帧回调说明](https://developer.mozilla.org/en-US/docs/Web/API/HTMLVideoElement/requestVideoFrameCallback)明确回调发生在新视频帧提交到合成器时。对异步解码风险的路线选择是本任务的工程判断，并不是该接口自身承诺atlas一定更自然。

## 一期动作时序建议（需看实际渲染再调整）

24帧、60fps、固定机位，总长约400ms。0帧为已经准备好的姿势，不能先抬很高才迟迟触弦。

| 时间/帧 | 身体与手爪 | 可验要点 |
| --- | --- | --- |
| 0 | 右爪放在音孔上缘近弦位置，腕放松；左爪稳握琴颈。 | 琴面前后关系明确，两爪都真实接触各自区域。 |
| 1–2 / 17–33ms | 右爪小幅进入弦面，腕主导，肘肩只作很小跟随。 | 音频仍立即触发；视觉首次接触目标在50ms内。 |
| 3–6 / 50–100ms | 一次连续拨过，适度腕转，克制的跟随。 | 一按只有一次主要穿弦，不能自己弹第二下。 |
| 7–14 / 117–233ms | 爪向琴面前侧抬离，再沿弧线回。 | 回程绕开弦面，避免看起来又反向弹一次；不倒放整个下拨镜头。 |
| 15–23 / 250–383ms | 回到预备，平稳减速；脚与琴不漂。 | 首尾位置和运动趋势相接；不靠整张画面晃动掩盖切换。 |

身体细节：腕的主要位移可取约一个爪宽的0.25–0.4，肘位移更小，肩更小；这只是造型尺度建议，不是实际乐器演奏测量。面部保持注意力而不每键夸张点头，呼吸/眨眼首版可以先省略，避免触弦比脸和身体的花活还不清楚。

精致感优先检查：脸与耳的轮廓、瞳孔高光、口鼻层次、爪体积、肩肘相接、吉他面板边线/音孔镶嵌/琴桥/六弦/品柱/旋钮、柔和接触阴影。不要给每个表面同一种塑料高光；琴弦不应比爪或眼睛更抢眼。静帧若像临时球体拼凑，不应靠提高采样数称为高质感。

## 连按和用户体验

1. 单击：一个真实input对应一个声响与一次主要触弦，完整收手后保持静止，不循环。
2. 按住：过滤键盘repeat，同一键从按下到松开只记一次；窗口失焦清掉held状态。
3. 恢复途中再按：从当前浮点姿态继续到最近的可拨准备点，不跳帧0，不排整段旧动画。足够慢的输入应有清晰一一对应。
4. 接触附近再按：先做短而看得见的离弦回弹，再触弦。用约25ms+25ms作为起测值；是待视觉确认的时序，不是自然度结论。
5. 极快输入：保留即刻声音，视觉只能以实际可辨速率处理。用一个待合并的最新目标，不能无限排队导致用户停手后猫还弹；提示“快速连按可能合并动作”。不能把计数合并藏成“全部都精准同步”。
6. 不用两幅整图crossfade“变顺滑”，它会暂时出现两只爪、两把琴或重影。真正过渡来自同一场景连续渲染的空间轨迹。

测试页主流程只要“点一下/键盘弹”和“录制→导出视频”，旁边收起慢看/压力测试/诊断计数。第一眼应看到角色和乐器，不是渲染参数面板。用普通词标明“Blender吉他测试”，提供回正式版链接；不要用“终极升级/精致完成/拟真演奏”诱导用户认可尚未验收的主观效果。

## 真实验收与停止条件

- 静帧0/2/6/12/23并排看：脸/体形/影子稳定，完整琴和双爪都在，爪不穿琴、琴颈不穿躯干，手臂与肩肘连贯。
- 原速和0.5x各看单按三次：每次只有一次主要拨弦，回程不会“顺便再弹一次”。
- 0.5秒间隔连续8次：8个声响/8次可辨动作，停手后400ms左右稳定，不补演。
- 0.15秒间隔连续8次：观察连续接触与抬爪，不只看计数；脚、琴与脸不抖，不出现帧0闪回。
- 0.08秒间隔与按住：验证合并有界、无声画无限积压、键盘repeat不制造多次录制。不能把这个极限测试宣称逐音精确。
- 真实录四次ASDF，再导出视频：下载后检查H.264/AAC或浏览器实际编码轨，逐帧找四次接触；不能只看页面canvas或点击计数。
- 冷加载/失败：未准备好时明确提示并禁止假装演奏；失败后保留正式版入口；手机实体扬声器与分享App兼容未测就写未测。

若连续两次小样仍出现爪穿琴、肩肘脱开或回程二次触弦，停止扩大帧数/音区/乐器，先修相机和接触几何。若模型明显不如当前橘猫，不替换正式首页，只发布有边界的测试入口供真实比较。

## 2026-10-28 静帧r2独立评审
