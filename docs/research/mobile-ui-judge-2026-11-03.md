# 手机体验独立评审 · 2026-11-03

范围：准备声音→演奏→看谱翻页→真人录制→导出／分享。评审者不修改产品代码，不参与平台后台，不重做猫美术。以下为本轮候选修改前的独立检查，尚不是新候选或正式平台验收结论。

## 初评：两项需要处理的手机问题

**P1：320×568首屏看不到可演奏琴键，声音入口也被截去下缘。**

真实IAB视口320×568，正式站和本地当前代码均可见完整猫／模式／乐器，但DOM测量为scene y232.30–432.30、soundEntry y534.30–578.30、melody-scroll y630.30–767.30。无横向页面溢出（scrollWidth320），问题是首个实际动作太靠下，不是CSS推测。390×844同版则键盘下缘767.30、音域按钮下缘813.30，刚好可同时看到。建议仅对短手机收紧标题、模式、猫舞台和选择区，保留完整猫，目标至少声音入口和实际可弹键在首屏；不要求强制横屏。

**P1候选：键面横向滚动与按下发声语义冲突。**

源码在手机上对`.melody-keys/.music-key`设`touch-action:pan-x`，每个键的`pointerdown`立刻`hit(code)`并写真人事件；`pointercancel`只清held，无法撤回已发音／已存事件。复用实际`interaction.test.mjs`的app fixture，模拟“开始记录→KeyA pointerdown→浏览器pointercancel、无pointerup→停止导出”，结果`audio.plays=["KeyA"]`，`JSON.events=[[0,0]]`。这证明取消不能撤回输入；**没有宣称已在实体手机重现滚动**。

建议明确产品取舍：若保留按下即发声的低延迟，键面使用`touch-action:none`，音域用已有低／高按钮或独立滚动轨道，不再承诺键面滑动无误弹。若坚持键面pan-x，需要清楚接受首音可能发出／录入的代价；不建议为了滚动在所有真人演奏上统一加长按等待。修改后需用相关事件fixture和真机补验证。

### 音域误录问题已按明确交互取舍解决

- 候选音乐键计算样式为`touch-action:none`，保留按下发声；新增独立`keyboardRange`。可见文案改为通过独立音域条或低／高按钮换音域，不再引导在键面拖动。
- 独立真实浏览器：开始记录，音域条Home→End，测得scrollLeft352=max352，录制显示14.3秒、**0次敲击**；随后仅激活C5与C4，再停止／导出。JSON恰好`[[14367,7],[14396,0]]`、duration14408ms。音域移动没有增加音符，完整高低音可达。
- 初评的pointercancel fixture仍说明“已发音不能撤回”；候选通过把导航从音乐键分离关闭误触导航风险，并不声称可以撤回已播放的真人音符。
